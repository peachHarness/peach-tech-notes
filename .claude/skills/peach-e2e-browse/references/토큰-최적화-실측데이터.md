# 토큰/속도 최적화 실측 데이터

이 문서는 `agent-browser`와 Playwright 계열 도구의 실측 자료를 보관한다.
정책 판단은 속도보다 안정성이 우선이다. E2E 기본 실행은 Playwright `targetId` 고정으로 한다.

### screenshot 이미지 토큰 실측 (2026-08-21, Chrome 153 Beta / CDP 9333)

같은 대상(카드형 패널)을 CSS 판정 vs 스크린샷으로 비교. 이미지 토큰은 `넓이×높이/750` 추정.

| 방법 | 크기 | 토큰 |
|------|------|------|
| `eval` CSS 판정(`getComputedStyle` 3속성 묶음) | 81B | **~25** |
| `screenshot` 요소 clip (454×214) + `Read` | 4.4KB | ~130 |
| `screenshot` 뷰포트 전체 (1409×988) + `Read` | 10KB | **~1,856** |
| `screenshot` 실제 관리자 화면 (1294×988) + `Read` | 95KB | **~1,705** |

**clip이 13배를 가른다.** 이미지 토큰은 픽셀 면적에 비례하므로, 사람 확인용으로 꼭 찍어야 하면
`page.locator('.대상').screenshot()`이나 `clip`으로 관심 영역만 좁힌다. 값으로 판정 가능한
항목이면 애초에 `eval` CSS 판정(~25토큰)이 요소 clip보다도 5배 싸다.

## 작업별 토큰 예산 가이드

| 작업 유형 | 권장 예산 | 방법 |
|----------|----------|------|
| 페이지 확인 | < 300B | `eval "document.title + ' \| ' + location.href"` |
| 텍스트 읽기 | < 1,500B | `eval "body.innerText.substring(0,N)"` (N 조절) |
| 요소 존재 확인 | < 10B | `eval "!!querySelector('.target')"` |
| 목록 일괄 추출 | < 2,000B | `eval "JSON.stringify(Array.from(...).slice(0,10).map(...))"` |
| 클릭 대상 찾기 | < 400B | `snapshot -i -c -s "관심영역"` |
| CSS·레이아웃 판정(테두리·색상·높이) | < 300B | `eval "(() => { const cs=getComputedStyle(el); return {borderRadius: cs.borderRadius, rect: el.getBoundingClientRect()}; })()"` |
| Flutter API 호출 | < 500B | `eval "fetch(...).then(...)"` → `eval "window.__result"` |
| **금지** | 50,000B+ | `snapshot` 전체, `screenshot` + `Read` |

## 도구 오버헤드 실측 (2026-07-30)

같은 작업(targetId 고정 → `title | url` 반환), Chrome Beta CDP 9333, 각 3회.

| 경로 | 입력 | 출력 | 평균 시간 | 기존 탭 |
|------|-----:|-----:|----------:|---------|
| `playwright-cli run-code` + 보일러플레이트 | 498B | 1,014B | 1,272ms | **`open`이 1개 파괴** |
| `pwx.js <targetId> title` | 126B | 70B | 606ms | 무손상 |
| 절감 | -75% | **-93%** | -52% | — |

출력 1,014B의 내역: 결과값 ~400B(대부분 Google 추적 파라미터) + 입력 스크립트 에코백 ~600B. `pwx.js`는 에코가 없고 URL을 `origin+pathname+?q=`로 정규화한다.

`open` 탭 파괴는 2회 재현됐다(openrouter 탭 → `about:blank`, 이후 google 탭 → `about:blank`). `attach`는 CDP endpoint에 붙지 않아 우회로가 아니다. 사용자 탭이 살아 있는 고정 프로필에서 `open`은 남의 작업을 지운다.

## eval click vs click ref — isTrusted 차이

| 방법 | isTrusted | 보안 폼 | 비용 |
|------|:---------:|:-------:|------|
| `eval "el.click()"` | false | 무시될 수 있음 | ~50B |
| `click ref` (snapshot 후) | true | 정상 동작 | ~400B (snapshot 포함) |

## 병렬 격리 실측

2026-06-01 Chrome Beta CDP 9222, fixture A/B 탭, 각 도구 50회 병렬 반복:

| 방식 | cross-tab 실행 | total | p95 | 판단 |
|------|---------------:|------:|----:|------|
| `agent-browser tab <label>` + `eval` 병렬 | 50/100 | 17,440ms | 365ms | 병렬 조작 기본값 금지 |
| Playwright `connectOverCDP` + targetId page | 0/100 | 82ms | 3ms | 병렬 조작 권장 |
| `playwright-cli run-code` + targetId page | 0/100 | 1,149ms | 5ms | CLI fallback 가능, 시작 오버헤드 큼 |

해석:

- `agent-browser`는 단일 읽기에서 빠르고 토큰 효율이 좋다.
- 같은 daemon을 공유하는 병렬 조작에서는 current tab race가 재현됐다.
- 병렬 실행이나 장시간 QA 재현은 targetId로 page를 고정한 Playwright 경로를 사용한다.

## Gmail 최근 메일 읽기 속도 실측

2026-06-01 Chrome Beta CDP 9222, 로그인된 Gmail 탭, 최근 메일 15개를 읽어 count/totalChars/checksum만 비교했다.
메일 제목과 본문은 기록하지 않았다.

| 방식 | run1 | run2 | run3 | 평균 | extract 평균 | 결과 |
|------|-----:|-----:|-----:|-----:|-------------:|------|
| agent-browser | 3,462ms | 2,784ms | 3,136ms | 3,127ms | 171ms | 15건, checksum 동일 |
| playwright-cli | 7,884ms | 5,806ms | 10,437ms | 8,042ms | 1ms | 15건, checksum 동일 |

해석:

- Gmail 단일 읽기 작업은 `agent-browser`가 약 2.6배 빨랐다.
- `playwright-cli`는 CLI/session/tab 준비 오버헤드가 커서 총 시간이 길었다.
- 두 방식 모두 같은 15건을 읽어 결과 정합성은 같았다.
- 하지만 병렬 탭 격리 검증에서 `agent-browser` current tab 간섭이 재현됐으므로 기본 도구로 채택하지 않는다.

## 최종 정책

| 상황 | 정책 |
|------|------|
| E2E browse 기본값 | Playwright CDP 또는 `playwright-cli` |
| scenario/suite/team-e2e | `E2E_TAB_ID=<targetId>` |
| 여러 AI 세션 병렬 작업 | Playwright targetId page |
| agent-browser | 사용자가 명시 요청한 단일 세션 읽기 전용 확인에만 opt-in |
| 반복 수정 중 시각 확인 | `getComputedStyle`/`getBoundingClientRect` 우선. `screenshot`은 최종 확인 시점에만, `Read`는 결과 보고 1회로 |
| 부득이한 screenshot | 뷰포트 전체 금지, `clip`/요소 screenshot으로 좁힌다(실측 13배차) |
